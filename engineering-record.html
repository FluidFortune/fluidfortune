ABSTRACT

Pisces Moon OS v1.2.0 ships a four-radio multi-app handheld operating system — preemptive multitasking, persistent dual-core background intelligence collection, runtime-loadable application modules, real-time SD logging, FAT32 file management — on a $50 microcontroller with 320 KB of internal SRAM and no external memory of any kind. For reference: the IBM-compatible Compaq Presario that ran Windows 3.1 in 1995 had 4 MB of RAM. The Cardputer ADV running Pisces Moon has one-twelfth of that. The Compaq ran cooperative multitasking. The Cardputer runs preemptive multitasking with concurrent WiFi, Bluetooth Low Energy, GPS, and LoRa radios all coordinating in real time. This is not a benchmark or a tech demo. It is a shipping operating system.

This engineering record documents how that became possible. Eleven engineering problems solved on the way — none of which had documented prior solutions on this hardware platform. Eight architectural patterns hardened into platform-level disciplines: the SPI Bus Treaty, the Ghost Engine task model, lazy app-state allocation, WiFi mode-locking with hard teardown, lazy boot initialization, runtime radio tuning, the three-layer ELF sandbox, and the three-tier memory architecture that allows the same OS to run from zero PSRAM through 8 MB PSRAM with a single codebase.

The deeper claim is in the methodology: name the constraint, document the protocol, make it a platform contract. The treaties this methodology produced — SPI Bus Treaty on the S3, UART Peripheral Map on the P4 — are the expressions. The methodology is the contribution. The Cardputer result is the proof that it generalizes to hardware the industry treats as incapable of running an OS at all.

The Espressif ESP32-S3 is a dramatically more capable chip than its marketing implies. The chip vendors sell it as a smart-home endpoint, an AI inference accelerator, a WiFi-and-Bluetooth IoT module. The chip is also the platform for what this document describes. The reference firmware did not show it. The vendor marketing did not describe it. The chip was always capable. The operating system is the proof.

I

THE THESIS — WHAT THIS DOCUMENT PROVES

The ESP32-S3 has been treated by the industry as a single-purpose appliance. The reference firmware that ships from chip vendors targets that model. The Arduino sketches that populate the maker ecosystem reinforce that model. The result is that most ESP32-S3 devices ship with software that uses a fraction of what the chip can do.

Pisces Moon OS demonstrates the other path. A single operating system, deployed across three physically different ESP32-S3 handheld devices, running 49 to 52 native applications on each with concurrent four-radio coordination on devices that have it, and a multi-app launcher with persistent state on devices that don't. The Ghost Engine never stops collecting on any of them. The SPI Bus Treaty arbitrates the shared bus on all of them. The same firmware codebase produces all three binaries.

This is not a benchmark. It is not a tech demo. It is a shipping operating system with eleven documented engineering problems solved, eight architectural patterns documented as platform-level disciplines, and a verifiable public codebase. The proof is not the claim — the proof is the code, the binaries, and the field validation.

This document is the engineering record of how Pisces Moon OS came to be possible on the ESP32-S3 hardware class. It is also, by accident, a description of what the chip is capable of doing when the operating system is treated as the engineering problem instead of an implementation detail.

The work began with the T-Deck Plus and a single, defining technical question: can persistent dual-core background tasking work on shared-bus hardware without crashing? The answer required inventing the SPI Bus Treaty. From there, the question expanded: can the same OS run on a second device with different GPIO assignments? That required Problems 7 and 8 and the hardware abstraction layer. Then: can it run on a device with one-twentieth the memory? That required Problem 11 and a complete reframing of how an embedded OS manages always-on app state. The pattern at each scale was identical: name the constraint, document the protocol, make it a platform contract.

The record below is what got built, in the order it had to be built, with the patterns that emerged when each problem turned out to be the same shape as the last.

II

THE CHIP VS THE MARKETING

Espressif's documentation for the ESP32-S3 is technically excellent. The technical reference manual is comprehensive, the SDK is well-maintained, and the silicon is genuinely well-engineered. Credit where due: this is one of the better-documented embedded platforms in current production.

The marketing copy is a different document. The ESP32-S3 product page describes a chip optimized for "AIoT applications," with selling points framed around AI inference acceleration via vector instructions, dual-band WiFi 802.11 b/g/n at 2.4 GHz, Bluetooth Low Energy 5, USB OTG, and the standard array of peripherals. It is sold as a building block for smart-home endpoints, voice assistants, smart-display controllers, and industrial IoT sensors. The implied use case is: a device that does one thing well, on WiFi, with optional BLE for setup.

This is not wrong. It is just incomplete. The chip ships with capability the marketing does not describe.

The asymmetry is not a criticism of Espressif. Their marketing targets the volume customers — the smart-home OEMs, the IoT module integrators, the AI accelerator buyers — who collectively ship hundreds of millions of devices and pay the bills. The marketing reflects the use cases their customers actually buy. Nobody at Espressif is wrong about what their chip is selling for. They are simply silent about what it is also capable of.

This document fills that silence. The clearest way to show what was left on the table is to compare the most resource-constrained Pisces Moon target — the Cardputer ADV with zero PSRAM — to a desktop computer from thirty-one years earlier:

The Compaq had twelve and a half times the RAM. It could not have done what the Cardputer does — not with that operating system, and not with a different one designed for hardware that size. Cooperative multitasking cannot safely run a radio scanner alongside a foreground app. There was no networking stack ready to coordinate four radios. The architectural primitives were not in place.

The Cardputer can do it because the operating system was designed for what the chip actually is. FreeRTOS provides preemptive scheduling. ESP-IDF provides direct hardware access without OS overhead. The SPI Bus Treaty arbitrates the shared bus. The WiFi mode-locking enforces radio mutual exclusion. The lazy app-state allocation keeps boot heap available for the radio drivers. Architecture was spent, instead of memory. Architecture written by hand, in C, against hardware primitives directly.

This is the asymmetry the marketing leaves unsaid. The Compaq spent memory on abstractions — window manager, GDI, message queues, app heaps, segment management — that gave general-purpose flexibility at the cost of efficiency. Pisces Moon spends architecture on specialization — Treaty mutex for one specific bus, mode-locking for one specific radio, lazy init for one specific boot path — that gives radio-handheld capability at the cost of being unable to run Photoshop. Both are operating systems. They optimize for different things. One ran on a $1,499 desktop. The other runs in a $50 pocket device. The chip in the pocket has dramatically less RAM. It is dramatically more capable.

The Compaq came with an operating system because the world of 1995 expected computers to ship with operating systems. The Cardputer comes with a SoC because the world of 2026 expects microcontrollers to ship with whatever you write yourself. Pisces Moon closes that gap.

This is what a microcontroller looks like when you give it a real operating system. The chip was always capable. The platform support was always capable. The radios were always capable. The missing piece was someone willing to put in the engineering hours to coordinate them and to keep saying this is solvable when conventional wisdom said it wasn't.

III

THREE DEPLOYMENT TARGETS — ONE OPERATING SYSTEM

Pisces Moon OS v1.2.0 "Multi-Device" ships from a single PlatformIO project that produces three distinct firmware binaries, one for each supported device. The codebase is unified. Hardware differences are isolated behind #ifdef DEVICE_* blocks and a hardware abstraction layer (hal_pins.h, hal_display.h, hal_input.h). The application code does not know which device it is running on. It calls pm_input_read() and gets keystrokes; it calls gfx->print() and gets text on whatever display the device has.

TARGET 1 — LILYGO T-DECK PLUS — TIER 1 — FIELD INTELLIGENCE DEVICE

ESP32-S3 at 240 MHz, 8 MB PSRAM, QWERTY keyboard, LoRa radio (SX1262), GPS (ATGM336H), WiFi, Bluetooth LE, I2S audio (ES8311), MicroSD storage, TCA8418 I2C keyboard controller. Retail: $50. The origin device — every architectural pattern documented in this record was first encountered, named, and solved on this hardware. 49 native applications. Ghost Engine on Core 0. Full SPI Bus Treaty implementation. Reference architecture for the platform.

TARGET 2 — LILYGO T-LORA PAGER — TIER 1 — FIELD INTELLIGENCE DEVICE (PORTED)

ESP32-S3 at 240 MHz, 8 MB PSRAM, QWERTY keyboard via TCA8418 I2C controller, LoRa radio (SX1262), GPS (MIA-M10Q), WiFi, Bluetooth LE, MicroSD storage. ST7796U 480×222 display. DRV2605 haptic driver. XL9555 I2C GPIO expander gating power to all peripherals. Retail: $45. 52 native applications. The successful port of v1.1.x → v1.2.0 surfaced four engineering problems unique to this hardware: GPIO 21 dual-function conflict (Problem 7), SPI bus state corruption requiring deferred SD mount (Problem 8), Ghost Engine silent failure under deferred mount conditions (Problem 9), and platform variant header path requirements. All resolved in v1.2.0. The Ghost Engine, SPI Bus Treaty, and Bridge protocol operate identically to the T-Deck Plus implementation.

TARGET 3 — M5STACK CARDPUTER ADV — TIER 1 — VALIDATED v1.2.0

ESP32-S3FN8 at 240 MHz, no PSRAM (320 KB usable internal SRAM only), 8 MB flash. Compact credit-card form factor. 240×135 ST7789 display. Full QWERTY keyboard. MicroSD slot. Built-in microphone. IR transmitter. M5Stack Cap expansion connector. With the Cap LoRa-1262 attached: adds SX1262 LoRa (27 dBm) and AT6668 multi-constellation GPS. Retail: $50. 47 native applications. The proof that the OS generalizes downward to the hardest version of the memory problem. Concurrent four-radio operation (WiFi + BLE + GPS + LoRa) confirmed with 125 KB free heap during active wardrive scanning. Problem 11 documents the architectural changes required.

The three-tier memory architecture is the defining property of the v1.2.0 release. The same OS, with the same application catalog, the same Bridge protocol, the same SPI Bus Treaty, runs on devices with zero PSRAM, 2 MB of PSRAM (Heltec V4 class — pending), and 8 MB of PSRAM, with hardware differences confined to #ifdef blocks. A wardrive log produced on Cardputer is byte-for-byte compatible with one produced on T-Deck Plus. A mesh message sent from Cardputer reaches T-LoRa Pager. A file saved to SD on one device can be read by the others.

The implication is not that the Cardputer was made to behave like a T-Deck Plus. The implication is that the OS was designed honestly enough that the same architecture survives across an order-of-magnitude difference in available memory. This is the platform claim: one operating system, three deployment targets, no compromises on the protocol.

IV

EIGHT ARCHITECTURAL PATTERNS

The patterns below are the platform-level disciplines that emerged from the engineering work. Each was discovered by encountering a specific failure mode, naming the constraint, and formalizing the response into a contract that every subsequent component of the OS honors. They are documented here in the order they were established. On PSRAM-equipped devices, some of them cost nothing and are invisible. On the Cardputer, they are the difference between "single-purpose firmware" and "multi-radio handheld computer."

PATTERN 1
The SPI Bus Treaty

The first known documented formal behavioral protocol governing shared-bus arbitration on the ESP32-S3. Four rules every OS component and ELF module developer must follow: hit-and-run (open, write, close, release immediately), no extended holds, radio traffic management via shared boolean flag, metadata-only destructive operations. Implemented as a recursive mutex (spi_mutex) with 500ms timeout, named ownership debug logging, ISR-safe variants, and per-device sentinel flags. 54 take sites across 12 files; 56 give sites verified. Audit document published as docs/SPI-TREATY-AUDIT.md. The full architectural whitepaper is at spi-bus-treaty.html.

PATTERN 2
The Ghost Engine Task Model

A persistent FreeRTOS task pinned to Core 0 that runs the radio intelligence collection workload continuously — wardrive, BLE scanning, GPS logging, mesh listening — independent of any foreground application activity on Core 1. The defining invariant is that the device is always collecting. The Ghost Engine has no visible interface. It produces no notification. To a casual observer, the device looks like a toy. To the operator, the Ghost Engine is the entire point. Every other architectural decision in the OS exists in service of one guarantee: the Ghost Engine never stops.

PATTERN 3 — THE TURNING POINT
Lazy App-State Allocation

This pattern is the moment the project stopped treating the chip as a microcontroller and started treating it as a computer that happened to be small. The framing change is more important than the technical change.

The technical change: every always-on app buffer was moved out of static memory and into app-lifetime allocations. Mesh Messenger channel buffers, audio player playlists, RetroPack ROM tables, ELF browser app lists, recorder file metadata — all moved to allocation on app entry, release on app exit. The OS no longer reserves RAM for dormant apps. Result on Cardputer: 81 KB of static memory returned to the heap before the user did anything. The static RAM footprint dropped from 190 KB to 109 KB. The free heap at task-spawn time rose from 97 KB to 219 KB.

The framing change: the embedded systems industry has a default assumption that always-on apps reserve always-on memory. This assumption is correct for single-purpose firmware where there is only one app. It is wrong for a multi-app OS, because a multi-app OS by definition has many apps that are not currently in use. The static-memory cost of "always-on apps in a multi-app OS" had never been recognized as the dominant memory pressure on this hardware class because no previous project had built a multi-app OS on it.

This is what unlocked the Cardputer. Before this pattern was applied, the honest read of the heap measurements was that concurrent multi-radio operation on a no-PSRAM ESP32-S3 was hardware-impossible. After this pattern was applied, it ran with comfortable headroom. The constraint was never the hardware. The constraint was an architectural assumption inherited from single-purpose firmware. Discipline: if an app's state is not in use, it does not belong in static memory.

PATTERN 4
WiFi Mode-Locking with Hard Teardown

WiFi-as-scanner (used by wardrive, packet sniffer, beacon spotter) and WiFi-as-client (used by Gemini, Bridge HTTP, file manager) cannot coexist on Cardputer within the available memory budget. The OS enforces the mutual exclusion at the WiFi-mode level rather than hoping users avoid the conflict. A central module (wifi_mode.cpp) tracks the current WiFi mode as a global enum and provides request_wifi_mode() as the gate. On mode conflict on Cardputer, the user is prompted; on confirmation, the current mode's resources are fully torn down (including NimBLE and the WiFi driver) and the new mode initializes fresh. ~61 KB reclaimed per teardown — sufficient headroom for the new mode. On PSRAM-equipped targets the same call is permissive. Discipline: enforce hardware constraints at the OS level honestly, not by hoping users do the right thing.

PATTERN 5
Lazy Boot Initialization

Defer subsystems that consume meaningful heap until first use. On Cardputer, the WiFi autoconnect logic and the Gemini chat client do not initialize at boot — they initialize on first use of a WiFi-client app or the Gemini chat app respectively, recovering ~25 KB at startup. Saved WiFi credentials still persist on SD via the wifi_manager module, so the user is not asked to re-enter their password. The Gemini client's idempotent-init pattern made the deferral safe with no API redesign. Discipline: if a subsystem can be initialized on first use without changing the user-facing behavior, defer it.

PATTERN 6
Runtime Radio Tuning When Build-Flag Tuning Fails

Arduino-ESP32 links against pre-compiled libraries (libbt.a) that bake the ESP-IDF sdkconfig defaults in at library compile time. Setting CONFIG_BT_NIMBLE_* as PlatformIO build flags only affects code that gets compiled fresh within the project — the underlying Bluetooth controller never sees these flags, producing init hangs when the two sides disagree on resource layout. The honest response: tune NimBLE at runtime via the API instead. Set the scan duplicate cache to a small bounded value, use passive scanning instead of active, disable result storage. These are unconditional wins applied in the Cardputer wardrive path. Discipline: when the build system cannot deliver the tuning you need, the runtime API often can. Document the failed path so the next developer doesn't repeat the experiment.

PATTERN 7
The Three-Layer ELF Sandbox

The first known documented hardware-enforced ELF module sandbox on the ESP32-S3 for a general-purpose OS. Layer 1: xt_set_exception_handler() registers a custom handler for PMS violation exceptions (EXCCAUSE_LOAD_PROHIBITED / EXCCAUSE_STORE_PROHIBITED) that intercepts before the ESP-IDF panic handler. If the faulting PC is inside the ELF PSRAM region, execution redirects to a fault trampoline in IRAM that kills the ELF task and returns the OS to the launcher — the Ghost Engine never pauses. Layer 2: direct register writes to the PMS base address (0x600C1000) mark OS SRAM read-only during ELF execution. Layer 3: ELF runs in a dedicated FreeRTOS task at priority 5 (below Ghost Engine priority 7) with semaphore-based completion signaling. Honest limitation: protects against buggy ELFs, not adversarial code. The PMS write-protects OS SRAM but cannot prevent an ELF from reading arbitrary addresses. No MMU means no virtual address spaces. Documented in v1.2.0 alongside the SPI Bus Treaty audit.

PATTERN 8
Three-Tier Memory Architecture from a Single Codebase

The PlatformIO build configuration is split into a shared base and per-tier build-flag groups. build_flags_psram contains BOARD_HAS_PSRAM, CONFIG_SPIRAM_USE_MALLOC=1, and the PSRAM cache workaround. T-Deck Plus and T-LoRa Pager inherit this block; Cardputer does not. The Cardputer environment instead defines DEVICE_NO_PSRAM and configures the allocator honestly — no PSRAM probe-and-fail path on every malloc, no false expectations baked into the memory model. The same source tree produces three binaries with different memory disciplines. Discipline: shared build flags should describe shared hardware capability. When the hardware differs, the build flags must differ — silently inheriting flags from a PSRAM-equipped sibling produces bugs that "just work" on the sibling and fail mysteriously on the variant.

These eight patterns are now the platform contract. New apps written for Pisces Moon are required to honor them. New hardware targets ported to the platform are tested against them. The pattern names themselves — SPI Bus Treaty, Ghost Engine, Mode-Locking, Lazy App-State Allocation — are the vocabulary the codebase uses internally and the documentation uses externally. They are the platform's idioms.

▌ THE CARDPUTER RESULT — WHY PROBLEM 11 IS DIFFERENT

Problems 1 through 10 were engineering work on hardware with 8 MB of PSRAM. They prove the operating system works. Problem 11 was building the same operating system on hardware with 1/25th of that memory. It proves the architecture works.

The Cardputer ADV ships with 320 KB of internal SRAM and no external memory of any kind. The ESP32-S3FN8 variant simply does not include PSRAM. When the v1.2.0 port began, the honest read of the heap measurements at the moment the wardrive task spawned — 97 KB free, with WiFi requiring 54 KB and NimBLE requiring 48 KB — was that concurrent multi-radio operation on this hardware was impossible. The industry's expectation for a no-PSRAM ESP32-S3 is single-purpose firmware. The chip is sold for that workload.

Three architectural changes — lazy app-state allocation, WiFi mode-locking with hard teardown, and PlatformIO PSRAM flag isolation — reclaimed 81 KB of static memory before the user did anything, established hardware-honest WiFi mode arbitration, and removed false PSRAM expectations from the allocator. The result: 219 KB free heap after WiFi STA init. 174 KB after NimBLE observer init. 125 KB free during active wardrive scanning with 24 BLE devices, 14 WiFi networks, and GPS lock at 27 satellites. Four concurrent radios. Real-time SD logging. Persistent multi-app state. 47 applications. On a chip with 320 KB total.

A Compaq Presario from 1995 had twelve times the RAM and could not have done this. Not because the Compaq was incapable, but because no operating system available for that hardware was designed to coordinate four concurrent radios with real-time bus arbitration on shared peripherals. The architectural primitives did not exist. The chip in the Cardputer has dramatically less memory and dramatically more capability — because the operating system was designed for what the chip actually is, not for what the marketing said it should be.

This is the engineering feat. Not the OS itself. The OS on this hardware. Eight patterns generalized from the PSRAM-equipped origin devices down to the no-PSRAM extreme of the same chip class, with no compromise on the application catalog, the Bridge protocol, or the Ghost Engine invariant. The Cardputer running Pisces Moon OS is the proof that the methodology generalizes. It is also, to the best of our knowledge, the most capable multi-radio handheld operating system shipping on a no-PSRAM microcontroller in the current market.

VI

THE METHODOLOGY — NAME THE CONSTRAINT, DOCUMENT THE PROTOCOL, MAKE IT A PLATFORM CONTRACT

Every problem in the table above was solved by the same three-step process.

First: name the constraint honestly. The SPI bus on the ESP32-S3 cannot be safely shared between the LoRa radio and the SD card under arbitrary task interleaving — that is the constraint. The Cardputer's internal SRAM cannot hold both the WiFi-STA driver state and the NimBLE Observer state simultaneously — that is the constraint. The Arduino-ESP32 framework's pre-compiled libraries do not respond to PlatformIO build-flag tuning of internal Bluetooth buffer counts — that is the constraint. Each constraint, once named, stops being a mysterious crash and becomes an engineering specification.

Second: document the protocol. The SPI Bus Treaty is a written document. The WiFi mode-locking rules are a written document. The lazy app-state allocation discipline is a written document. The PlatformIO build-flag isolation is a written document with a historical note explaining why the alternative approaches were tried and failed. Future developers — including future versions of the author — encounter the protocol before they encounter the failure mode it prevents. The documentation is the architecture.

Third: make it a platform contract. Every component of the OS is written to honor the protocol. Every ELF module developer is required to honor the protocol. New apps are reviewed against the protocols. New hardware targets are tested against them. The protocols are not suggestions or guidelines — they are the conditions under which the OS works at all. Violating the SPI Bus Treaty causes Guru Meditation errors. Violating the WiFi mode contract triggers a modal dialog and a hard teardown. The contract is enforced by the architecture itself, not by developer discipline alone.

The methodology is the invention. The treaties are its expressions.

This is what generalizes across hardware. The SPI Bus Treaty applies to one specific hardware constraint on the ESP32-S3. The methodology that produced it produced the UART Peripheral Map on the ESP32-P4 (where the constraint is different but the principle is identical), the four-core convention for P4's HP0/HP1/LP/C6 architecture, the WiFi mode-locking discipline for memory-constrained variants, the lazy app-state allocation discipline for static-memory pressure. Different problems, same shape. Different protocols, same methodology.

The architectural contribution of Pisces Moon OS is not any specific protocol. The architectural contribution is the methodology that turns ad-hoc workarounds into platform contracts. That generalizes. That is portable. That is the part that matters when this hardware class evolves and the next set of constraints emerges.

VII

WHAT'S NEXT

v1.2.0 "Multi-Device" is the platform proof. Three devices, one OS, eleven problems documented, eight patterns hardened. The work past this point is extension, not bring-up.

The methodology now extends to a different SoC family entirely. First boot on ESP32-P4 hardware was confirmed May 13, 2026. The P4 is dual RISC-V HP cores at 360 MHz with 32 MB HEX PSRAM, a separate ESP32-C6 connected via SDIO for radio operations, an LP core available as a Sentinel watchdog, and MIPI-DSI display output. The Ghost Engine no longer runs on shared silicon — it runs on dedicated hardware (the C6) with its own processor and its own clock domain. The methodology that produced the SPI Bus Treaty produced new protocols here: a formal UART peripheral map governing four serial controllers across four physical connections, and a four-core convention assigning explicit named roles to each processing unit. Different hardware. Same governance principle.

P4 development is rapidly evolving. The launcher renders. 57 apps register. The build framework is in place. The remaining work is application-level: porting the wardrive dashboard pattern across the other reference apps, implementing the status bar and control center, wiring the C6 bridge for promiscuous WiFi capture, integrating BLE on the new framework. None of this is bring-up effort. It is forward motion on a working platform.

The Pisces Moon project's near-term roadmap also includes the addition of a stationary deployment variant on Heltec V4 hardware (ESP32-S3R2 with 2 MB PSRAM, SX1262 LoRa at 27 dBm, AT6668 GPS, 2800 mAh battery with solar charging) — adding a third memory tier between Cardputer (0 PSRAM) and the LilyGO devices (8 MB PSRAM). This will validate the platform across the complete memory range of the ESP32-S3 class and demonstrate that the architectural patterns documented in this record generalize cleanly to additional hardware variants.

What this engineering record does not yet document is what comes after the embedded targets are exhausted. The Linux distribution (Pisces Moon Linux), the Android APK target, the Luckfox Pico 86 Panel, and the cross-platform Trojan Horse application runtime all exist. They constitute Tier 2 of the platform — sovereign computing on hardware the industry has declared obsolete. They have their own engineering record. They will be documented separately when the work to consolidate them reaches the same level of formal architectural completeness as the ESP32-S3 work documented here.

THIS IS WHAT THE CHIP IS, WHEN THE OPERATING SYSTEM IS REAL.

The ESP32-S3 was always capable of what this document describes. The reference firmware did not show it. The chip vendor marketing did not describe it. The Arduino ecosystem reinforced a single-purpose-firmware paradigm that left the rest of the chip's capability on the table. Pisces Moon OS is what happens when an embedded chip is treated as a computer instead of a peripheral. The chip is the hero. The operating system is the proof.
